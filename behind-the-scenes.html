How an agent builds a keynote

The language model never touches the computer. It writes requests as text – read_file, write_file – and the agent program checks them against the rules and runs them. The offline run took 23 such steps:

[1]    35s  read_file journal.md; read_file inputs/rahmen.md; read_file inputs/quelle_keynote.md
[2]    60s  read_file specs/tasks/build-session.md
 …
[7]   689s  write_file materials/01-giz-keynote/README.md      ← first full draft
[9]  1545s  write_file materials/01-giz-keynote/README.md      ← revision after self-review
 …
[20] 2611s  write_file agent_report.md
[23] 2812s  All self-checks pass …

Full log: run.log · task: T1.md · agent report: agent_report.md

Pros and cons

ProsCons
V1 Offline
  • no cloud cost
  • data never leaves the university
  • clean syntax
  • follows brief and fact sheet faithfully
  • slow (46 min)
  • copies the fact sheet almost word for word
  • jargon kept, crowded slides
  • its own self-check said “all fine” – and gave a wrong date
V2 Cloud only
  • best keynote straight away
  • plain words, clear tables
  • self-review caught jargon
  • ready in 4 min
  • highest cloud cost
  • all material goes to a cloud provider
  • still needs the speaker's review
V3 Offline + improve
  • quality on the level of V2, with a thread of people (Amina, Grace, Joseph, Sara)
  • ≈ 64 % fewer cloud tokens than V2
  • offline part can run overnight
  • two steps, ≈ 50 min in total
  • only about 55 % of the offline draft survived
  • the draft still goes to the cloud

What this means for GIZ projects

Local open models are good enough for first drafts
– and keep sensitive data in the country.
Quality comes from the improvement step
by a stronger model and by people.
Mix and match
offline for volume and privacy, cloud for polish – at about a third of the cloud cost.
Never trust the AI's own quality report
check it yourself.
The local model does the heavy, routine part. A stronger system – and finally a human – checks, shortens and makes it human.
